# Work order — the §9.1 burn-in battery and its ledger

> Burn-in exit (§9.1) has a criterion no engineering can compress: **"at least
> 14 consecutive days without an uncontained authority or duplicate-dispatch
> incident."** The clock starts with the first recorded work item. This packet
> exists so that clock starts now, in parallel with INT-4b/c/d.
>
> Correction for the record: this clause has been cited all week as "§21.2".
> It is **§9.1** of `docs/HARNESS_INTEGRATION_PLAN.md`. Every prior reference
> should be read as §9.1.

## What §9.1 actually demands (quoted, not paraphrased)

- ≥ 20 eligible low-risk Harness work items across ≥ 3 task families
- ≥ 14 consecutive days without an uncontained authority or duplicate-dispatch
  incident
- 100% correlation from task through run and handoff, and through PR when
  present
- zero unverified PR openings
- successful completion of all INT-4 failure drills *(tracked by the INT-4
  ledger, not this battery)*
- measured completion, verification, cost, and latency no worse than the
  **approved thresholds** — *no thresholds exist yet; this battery produces the
  measurements the operator approves them from*
- explicit operator decision to retire each fallback independently *(operator,
  later, outside this packet)*

## 1. Deliverable D1 — the battery runner

`scripts/ceremony/run-burnin-batch.mjs`: one invocation runs **one batch** — one
work item per green family (`lint-format`, `docs-fix`, `add-unit-test`,
`small-refactor`), each a full supervised lifecycle through the real dispatcher,
kernel, and container, exactly as the INT-2 suite runs them, with **unique work
item ids** (`burnin-<date>-<seq>-<family>`).

Reuse the suite's machinery (bring-up, scripted worker environment, teardown
ordering). Do not fork it — a battery that drifts from the suite proves things
about the battery.

Each batch also runs one **red sentinel** (`lint-format-red`): a deliberately
failing item proving refusal-correctness continues at scale. It is recorded but
**never counted** toward the 20 — a battery that counts its own sentinel is
padding.

`--evidence <dir>` is **required**. Refuse to run against a default temp path —
the suite's evidence-on-teardown loss already cost one full diagnosis cycle this
week.

## 2. Deliverable D2 — the burn-in ledger, append-only

`docs/evidence/burnin/LEDGER.jsonl` — one line per work item, written at batch
end from the run's own records (task row, decision records, Harness run status),
never from the runner's intentions:

```
{ ts, workItemId, family, taskVersion, intendedRunId, boundRunId,
  lifecycle, harnessOutcome, verificationVerdict, criteria: [...],
  handoffDecisions: n, prOpened: bool, effectsMutates: bool,
  elapsedSeconds, verificationSeconds, modelTokens, alerts: [...] }
```

Plus `docs/evidence/burnin/SUMMARY.md`, regenerated by the aggregator (D3) —
never hand-edited.

The invariants each line must witness, straight from §9.1:

- `intendedRunId === boundRunId` and exactly **one** bound run per work item
  (the correlation criterion)
- exactly one `handoff` decision for a green item; zero for the red sentinel
- `prOpened === false` — this battery never actuates; **any** true is an
  incident, recorded as such, never silently dropped
- `effectsMutates === false`

## 3. Deliverable D3 — the aggregator, and its honesty

`scripts/ceremony/burnin-status.mjs` reads the ledger and reports, per §9.1
criterion, **progress and violations**:

```
items: 8/20   families: 4/3   span: 2.1 days of 14
incident-free: true (0 incidents)
correlation: 8/8   unverified PR openings: 0
latency p50/p95 per family · cost (tokens) per family
```

Rules that make it honest:

- An item with missing or ambiguous evidence counts as a **violation**, never as
  progress. Absence is not success.
- The 14-day span is `newest_item_ts − oldest_incident_free_ts`, computed from
  ledger timestamps only — no wall-clock claims the ledger cannot back.
- An incident **resets the span start**; the ledger keeps the incident line
  forever. No deletion path exists.
- Duplicate `workItemId` or duplicate `boundRunId` across lines → violation,
  loudly.

## 4. Deliverable D4 — prove the aggregator can scream

Mutation proofs, each seen red then restored, INT-3c style:

| mutation | must |
|---|---|
| append a ledger line with `prOpened: true` | incident reported, span reset |
| append two lines sharing one `boundRunId` | duplicate-dispatch violation |
| append a line missing `verificationVerdict` | counted as violation, not progress |
| delete a line from the middle of the ledger | aggregator detects the seq gap or count mismatch and refuses the summary |

The last row needs a tamper-evidence mechanism — a per-line sequence number is
sufficient. Cryptographic chaining is **not** required; this is drift detection,
not an adversary model.

## 5. What the operator does with it

- Runs `run-burnin-batch.mjs` on whatever cadence suits — daily batches reach
  20 items in a week while the 14-day clock runs. The runner must be one
  command plus the evidence flag.
- After ~2–3 batches, reviews the measured latency/cost distributions and
  **approves thresholds** (a dated note in `SUMMARY.md`'s header block, written
  by the operator, the one hand-edited field). Until approved, the aggregator
  reports measurements with `thresholds: not yet approved` — it does not invent
  defaults.

## 6. What must not change

The INT-2 suite and its count sites · the INT-3b suite · `alerts.ts`, the
dispatcher, the kernel, the watchdog · the fixtures' budgets (the battery uses
them as merged) · ceremony docs.

## 7. Out of scope

Actuation of any kind (`prOpened` must stay false) · real repositories · real
credentials · INT-4b/c/d mechanisms · threshold enforcement (measurement only
until the operator approves values) · CI scheduling of batches (operator-run
for now; automation is a later decision).

## 8. Decisions

1. **The battery reuses the suite's machinery.** A parallel implementation
   would burn in the battery, not the system.
2. **The red sentinel is recorded, never counted.** Refusal-correctness at
   scale is evidence; padding the count is not.
3. **Absence is violation.** Missing evidence, missing verdicts, and ledger
   gaps all count against, never for.
4. **Thresholds come from measurement, approved by a human.** The aggregator
   never invents them.
5. **The clock is ledger-derived.** 14 consecutive days means 14 days of
   ledger-backed, incident-free items — not 14 days since someone remembers
   starting.
